# @_linked/livekit

Self-hosted LiveKit adapter for `@_linked/live-sessions`. The `./server` entry is for trusted server code; it signs short-lived room-specific credentials and acknowledges participant removal. The `./client` entry connects browser/desktop clients and applies track subscription preferences. The root entry has only a capability report and types.

An application must authenticate the caller, resolve Linked policy, hold the seat lease, and issue through `issueCredential` from `@_linked/live-sessions`. Use a separate physical LiveKit room for each private or protected audience and for each generation. A client can request tracks again after `updateSubscriptions(false)`; `applySubscriptions` is for bandwidth, never child safety or private-room authorization. `revoke` confirms the media service processed removal but does **not** prevent an unexpired token from rejoining. On a protected-policy change, move admitted people into a new generation room and retire the old room; keep grants at 60 seconds or less. A deleted room may be auto-created by a still-valid old token, but approved participants must no longer be there.

Pinned/tested SDK targets: self-hosted LiveKit server 1.13.7, client 2.22.3, server SDK 2.19.1. A local browser probe confirmed join, camera-source denial, removal, old-token rejoin and new-generation join. A `removeParticipant` call with `revokeTokenTs` did **not** block old-token rejoin in that pinned probe, so this adapter does not claim it as enforcement. Server-enforced per-listener track ACL remains unsupported. `./client` is a browser SDK adapter; native console clients require their own bindings.

Once `@_linked/live-sessions` 0.1.0 is published, run `npm install && npm test && npm run typecheck` and commit the generated lockfile. Until then this package can be built in the sibling local workspace. Publish `live-sessions` first so this standalone repository's dependency can resolve.

The optional `npm run test:e2e` runs a headed-media-capable Chromium probe against a disposable self-hosted LiveKit 1.13.7 server on loopback. Start the server with `docker run -d --rm --name linked-fw-livekit-test -p 127.0.0.1:7880:7880/tcp -p 127.0.0.1:7881:7881/tcp -p 127.0.0.1:7882:7882/udp livekit/livekit-server:v1.13.7 --dev --bind 0.0.0.0 --node-ip 127.0.0.1`, run the test, then `docker stop linked-fw-livekit-test`. This test intentionally asserts the pinned server's current old-token reuse behavior; a server upgrade that changes it should trigger a review of the adapter capability report.
